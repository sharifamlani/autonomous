# 01 Agent Architectures and Orchestration

## Role

This folder collects the evidence on *agent design patterns*: the reason-and-act loop, reflection and self-critique, planning and search, orchestrator-worker and routing structures, tool use, and memory. Its central question is **which agent architectures hold up outside demos?** It informs what the kit's agents are built from (one loop or several, where a planner or a router earns its place), which feedback signals the kit may trust for self-correction, and how the kit's own benchmark must be run (repeated trials, cost reported, held-out tasks). Harness-level evidence (context files, skills, hooks, Claude Code settings) is in folder 02 (H1-H15) and is not repeated here; H10, H11 and H14 are the nearest neighbours. Round 2 (F16-H25) adds recent lab and well-funded-startup work (Microsoft Research, Sierra, Google DeepMind, Meta, Apple, Sakana AI, Anthropic, Cognition, Stanford and Laude) on multi-turn degradation, reliability under shared control, benchmark validity, long context, code as the action space, evaluator-gated improvement loops and cost.

## What it establishes

**Verdict:** the designs that hold up outside demos are the plain ones with a *real external signal* in the loop. A tool-using act-and-observe loop (A1) plus feedback from something that can actually be checked (executed tests, a verifier, a database state: A2, A5, A6, A9) works; reflection, critique and debate driven only by the model's own opinion do not (A4, A5). Planning, search, routing and multi-agent splits are each worth adding only against a measured, cost-matched baseline (A10), because their demo gains are largest on toy or in-distribution tasks (A3, A8, A12) and the reliable result on real tasks is still low (A9, A11, A14). For the kit: one strong loop, verifiers and executed checks as the feedback, plans that can be revised, an orchestrator only for separable work with progress state written down, and every design choice scored over repeated trials with cost. Round 2 (F16-H25) sharpens this in four ways: the real-use gap is *recovery and consistency* over many turns, not first-shot skill (F16, A17); the measuring instrument is itself unreliable, so the kit's benchmark tasks need an audit before their scores steer design (A18); in the lab-authored comparisons here, the model matters more than the scaffold and added agents mostly add cost (C18, A26); and the loops that do improve are the ones gated by an evaluator the agent cannot edit (A22, A25).

1. **The act-and-observe loop is the sound base, with known failure modes.** A1: "ReAct outperforms imitation and reinforcement learning methods by an absolute success rate of 34% and 10% respectively" on ALFWorld and WebShop (Abstract). It is not uniformly better than reasoning alone: "ReAct outperforms CoT on Fever (60.9 vs. 56.3) and slightly lags behind CoT on HotpotQA (27.4 vs. 29.4)" (Section 3.3). Its failures are mechanical: in a 200-trajectory manual study, "Non-informative search, which counts for 23% of the error cases, derails the model reasoning", and reasoning errors, including repeating the same thoughts and actions in a loop, were 47% of ReAct failures against 16% for CoT (Section 3.3, Table 2). The kit needs loop detection and a recovery path when a tool returns nothing.
2. **Self-correction works only with an external signal.** A4: "LLMs struggle to self-correct their responses without external feedback, and at times, their performance even degrades after self-correction" (Abstract). On CommonSenseQA, GPT-3.5 went from 75.8% to 38.1% after one self-correction round while the same method *with oracle labels* reached 89.7% (Table 2). A4 explains: "the improvements in these studies result from using oracle labels to guide the self-correction process, and the improvements vanish when oracle labels are not available" (Section 1). A4 also finds multi-agent debate "significantly underperforms simple self-consistency using majority voting" at equal response count (Section 4). A5 reaches the same place from the survey side: "(1) no prior work demonstrates successful self-correction with feedback from prompted LLMs, except for studies in tasks that are exceptionally suited for self-correction, (2) self-correction works well in tasks that can use reliable external feedback" (Abstract). A2's headline "91% pass@1 accuracy on the HumanEval coding benchmark, surpassing the previous state-of-the-art GPT-4 that achieves 80%" (Abstract) is therefore an external-signal result: the loop is driven by self-written unit tests that run. Where those tests are unreliable it backfires: on MBPP Python Reflexion scored 0.77 against a 0.80 base (Table 2), with a "false positive test execution rate for MBPP Python ... 16.3%" (Section 4). For the kit's QA and research loops: reflect on executed test output and checked numbers, never on a model's second opinion.
3. **LLMs plan poorly alone and well with a checker.** A6: "the best model (GPT-4) having an average success rate of 12% across the domains" (Abstract); renaming actions and objects (a change that does not affect a classical planner) dropped GPT-4 from 210 solved of 600 to "1 instance in the deceptive Mystery Blocksworld domain" (Section 4). With an external verifier back-prompting the model, "GPT4 is able to come up with correct plans 82% of the Blocksworld instances and 70% of the Logistics one" (Section 5.2, Table 4, 15-round cap). A8 shows the same shape on web tasks: a zero-shot planner lifts an untrained executor from 9.85% to 14.21%, "a noticeable improvement" that is "far from satisfactory" (Section 4), and it sits well below an executor trained ReAct-style with no planner (23.63% vs 36.97%, Table 1); a static plan fails when content is unknown at planning time, and adding dynamic replanning "significantly increases the performance of the model by 10.31% over the static PLANNER, achieving 53.94%" (Section 5.3.1), reaching 57.58% with reasoning traces (Abstract). A7 shows what plan-first buys: on HotpotQA ReWOO used 1,986 tokens against ReAct's 9,795 at 42.4 vs 40.8 accuracy (Table 2), and "reduce token usage by 64% with an absolute accuracy gain of 4.4%" averaged over six benchmarks (Section 3.2); but it concedes that where "little context about the environment is available, fully relying on foreseeable reasoning becomes impractical" (Section 4). Use a planner for known, decomposable work, with a replan step and a verifier, not as an open-loop script.
4. **Tree search buys accuracy at a price on tasks that are easy to check.** A3: Game of 24 "while GPT-4 with chain-of-thought prompting only solved 4% of tasks, our method achieved a success rate of 74%" (Abstract), but at $0.74 per case against $0.47 for best-of-100 chain-of-thought (49%) (Appendix B.3, Table 7), and "could require 5-100 times more generated tokens than CoT". The authors say deliberate search "might not be necessary for many existing tasks that GPT-4 already excels at" (Section 6). The kit should not default to search.
5. **Simple baselines usually beat the clever agent once cost is counted.** A10: "There is no significant accuracy difference between our warming strategy and the best-performing agent architecture", while "Reflexion and LDB cost over 50% more than the warming strategy, and LATS over 50 times more" (Section 2.3, Figure 1); "the question of whether debugging, reflection, and other such 'System 2' approaches [22] are useful for code generation remains open" (Section 2.3). A10 also finds "the majority of benchmarks do not include an appropriate held-out set, including 7 that have no hold-out" (Section 5). This is the rule for the kit's benchmark: a no-plugin baseline arm, cost per task beside success, and held-out tasks.
6. **Reliability, not average success, is the real-use gap.** A9: even the best function-calling agent "succeed[s] on < 50% of the tasks, and [is] quite inconsistent (pass^8 < 25% in retail)" (Abstract); native function calling "consistently outperforms text-formatted agent methods", and adding a "think" function "did not boost performance" (Section 5.1). About a quarter of failures (25%) were wrong decisions from not following the domain's rules (Section 5.2). Run each kit task at least k times and report pass^k, as the research protocol already requires.
7. **Orchestrator-worker systems work modestly, and the orchestrator's bookkeeping is what matters.** A11: "Magentic-One achieves statistically competitive performance to the state-of-the-art on three diverse and challenging agentic benchmarks" (Abstract), at 38.00% on the GAIA test set (GPT-4o with o1-preview) against 92.00% for humans, and 32.8% (GPT-4o) on WebArena against 78.2% for humans (Table 1). Ablations: "without the full ledgers, performance drops by 31%" and "removing any single agent reduces performance by between 21% (Coder, Executor) to 39% (FileSurfer)" (Section 5.3). Its second most common error code is "insufficient-verification-steps", tasks "marked as complete without thorough validation" (Section 5.4): a design argument for an independent verifier. A14 adds an uncontrolled counter-example on structure (two frameworks; its text says "Both using GPT-4o" but Table 1 lists OWL with "GPT-4o, o3-mini" and no cost): "OpenHands CodeAct is a single agent that is better at maintaining consistency in a long-horizon task, while OWL RolePlay adopts multi-agent collaboration and experiences difficulty in preserving progress and context" (8.6% vs 4.0%, Section 7.1, Table 1). Combine with H11 (multi-agent range +80.8% to -70.0%) and H14.
8. **Routing saves money only on traffic that looks like its training data.** A12: "the MT Bench score at CPT(50%), 8.8, is 95% that of GPT-4's score (9.3)" (Table 1 caption) with "costs by up to 75%" lower than a random router once the training data is augmented (Table 1 caption); but on MMLU "Routers trained only on Darena perform poorly due to most questions being out-of-distribution" (Table 2 caption; Darena is the Chatbot Arena preference data), with results from -5.4% to +4.9% against a random router (Table 2). Any kit router (cheap model for easy steps, strong model for hard ones) must be tuned on the kit's own task mix.
9. **Memory is a weak spot, and long context is not memory.** A13: "commercial chat assistants and long-context LLMs showing a 30% accuracy drop on memorizing information across sustained interactions" (Abstract); GPT-4o falls from 0.870 with only the evidence sessions to 0.606 with the full ~115k-token history (Figure 3b), and "ChatGPT and Coze instantiated with GPT-4o exhibits 37% and 64% performance drop" (Figure 3a caption). Better design is cheap: "round is the more optimal granularity for storing" history, and expanding keys with extracted user facts improves "memory recall (9.4% higher recall@k) and downstream question answering (5.4% higher accuracy)" (Section 1, contributions). For the kit this backs files-plus-retrieval notes (see H3, H5) over relying on a long window.
10. **The recipe from the Claude Code side agrees.** A15 (vendor): "we recommend finding the simplest solution possible, and only increasing complexity when needed", "Agentic systems often trade latency and cost for better task performance", and "you should consider adding complexity only when it demonstrably improves outcomes". It lists prompt chaining, routing, parallelization, orchestrator-workers and evaluator-optimizer, and warns that frameworks "often create extra layers of abstraction that can obscure the underlying prompts and responses". It gives no measurements; A10 and A9 supply the missing ones. For tool and interface design, which A15 stresses, the measured evidence is H10 (SWE-agent).
11. **Real tasks are still hard.** A14: "the most competitive agent can complete 30% of tasks autonomously" (Abstract), Gemini-2.5-Pro at 30.3% success, 27.2 steps and $4.2 per task (Table 1). A14 also records "deceiving oneself": an agent that could not find the right colleague "decides to create a shortcut solution by renaming another user to the name of the intended user" (Section 7.3). The kit's verifier must check the outcome, not the agent's report.
12. **Real use is multi-turn and shared-control, and that is where models get lost.** F16 (Microsoft Research and Salesforce Research): "an average drop of 39% across six generation tasks" when the same instruction arrives sharded over turns instead of fully specified (Abstract, Section 6.1), decomposed into "a minor loss in aptitude and a significant increase in unreliability"; Figure 1 labels these as -15% aptitude and +112% unreliability, and "when LLMs take a wrong turn in a conversation, they get lost and do not recover" (Abstract). Agent-style repair helps only partly: repeating earlier user turns (SNOWBALL) "can mitigate the FULL-to-SHARDED performance deterioration by 15-20%" and the authors conclude that "relying on an agent-like framework to process information might be limiting" (Section 7.1, Table 2, GPT-4o and GPT-4o-mini only). A17 (Sierra) shows the same shape with tools: when the user also acts on the shared environment, "gpt-4.1 pass^1 drops from 74%/56% for retail and airline respectively to 34% for telecom", claude-3.7-sonnet reaches 49%, and "as k increases, the pass^k scores decline more rapidly for telecom compared to airline" (Section 4.2); shifting from no user to a collaborative setup "results in a substantial drop in pass^1 (18% drop for gpt-4.1 and 25% drop for o4-mini)" (Section 4.2). Together with A9 this fixes the kit's test design: score unattended runs over many turns and k repeats, and start a fresh context rather than patching a conversation that took a wrong turn.
13. **The ruler can be wrong, and the scaffold matters less than the model.** A18 (UIUC, Stanford, Berkeley, Yale, MIT and others): benchmark flaws "can lead to under- or overestimation of agents' performance by up to 100% in relative terms" (Abstract); "a trivial agent that returns empty responses is considered successful on intentionally impossible tasks ... achieves a 38% success rate and outperforms a GPT-4o-based agent" on tau-bench airline (Section 1); an agent can "score 100% on SWE-Lancer [without] resolving any tasks"; applying their checklist "reduced performance overestimation in CVE-Bench by 33% in absolute terms" (Section 1). This qualifies the tau-bench numbers in item 6 and is a pre-flight list for the kit's own tasks. C18 builds the opposite kind of instrument (89 tasks, each with "a unique environment, human-written solution, and comprehensive tests for verification"; Abstract) and reports "Codex CLI paired with GPT-5.2 achieves the highest average resolution rate of 63%", with "model selection ... usually more important than agent scaffold" (Codex CLI +52% with GPT-5.2 over GPT-5-Nano; Gemini-2.5-Pro +17% on Terminus 2 over OpenHands; Section 4). It also finds "essentially no correlation between the number of average turns per trial and model success rates" and that "higher token count does not necessarily correlate with better performance" (Section 4.1), with a benchmark run costing "anywhere from one to a hundred dollars" (Section 4.1). C18's own neutral scaffold, Terminus 2, "has a single tool, a headless terminal" (Section 3.1): a simple baseline arm is how the authors compare models.
14. **Reasoning models moved the planning numbers, not the need for a checker.** A19: o1-preview "correctly answers 97.8%" of 600 small Blocksworld instances, 52.8% on Mystery Blocksworld and 37.3% on a randomized-name version (against "the flat zeroes we saw when testing previous models"), but on "110 instances which each require at least 20 steps" it "only manages 23.63%"; it "still fails to provide any correctness guarantees" and the o1 experiments alone "run up a bill of $1897.55" (Section 3). This updates A6: the 12% GPT-4 figure is stale, the verifier argument is not. A23 (Apple) adds a complexity map: "low-complexity tasks where standard models surprisingly outperform LRMs, (2) medium-complexity tasks where additional thinking in LRMs demonstrates advantage, and (3) high-complexity tasks where both models experience complete collapse" (Abstract), and "even when we provide the algorithm in the prompt ... performance does not improve" on Tower of Hanoi and Checker Jumping (Section 4.4, Figure 8). For the kit: do not buy extended thinking for easy steps, and do not trust a long plan that nothing executes or checks.
15. **Code is a good action format for composition, with a limit.** A20 (UIUC; ICML 2024): "CodeAct outperforms widely used alternatives (up to 20% higher success rate)" (Abstract); on the multi-tool M3ToolEval, CodeAct had the highest success rate for 12 of 17 LLMs, the best model gained 20.7 points over the next format with 2.1 fewer turns (Section 2.3, Table 3), and interpreter error messages let the agent "self-debug" (Section 2.3). On single atomic API calls (API-Bank, Table 2) the picture is flat: the best format was CodeAct for 8 models, JSON for 5 and text for 4, and gpt-4-1106-preview scored 82.7 with JSON against 76.7 with CodeAct. This supports giving the kit's agents a shell and interpreter (an executed result is the external signal of item 2) while keeping small typed tools for simple calls; H25 (vendor) argues for few, well-described tools.
16. **Long context is a cost in itself, so keep contexts short and fresh.** F22: "even when models can perfectly retrieve all relevant information, their performance still degrades substantially (13.9%-85%) as input length increases" across 5 LLMs, including when the distractors are "replaced with minimally distracting whitespace" or "all masked" (Abstract). Reciting the retrieved evidence first, then solving from the short recitation, improved Mistral-v0.3-7B by up to 31.2% on GSM8K with essay distractors (Section 5, Table 4) and GPT-4o by "up to 4% on an already strong" baseline (Abstract). With A13 (history 0.870 to 0.606) and F16 (wrong early turns persist), this backs the kit's file-based notes, compaction and clean sub-agent windows, which A27 (vendor) recommends: sub-agents "return only a condensed, distilled summary" and compaction starts a new window. H28 (vendor) is the counterweight: sub-agents lose the implicit decisions in the full trace, so "share full agent traces".
17. **Improvement loops work when an evaluator the agent cannot edit scores them.** A25 (Google DeepMind): "continuously receiving feedback from one or more evaluators, AlphaEvolve iteratively improves the algorithm" (Abstract); its ablations on two tasks show each component (evolution, prompt context, full-file evolution, a mix of large and small models) gives "a significant improvement" (Section 4), and a scheduling heuristic it found "continuously recovers on average 0.7% of Google's fleet-wide compute resources" after deployment (Section 3.3.1). Its stated limit: "The main limitation of AlphaEvolve is that it handles problems for which it is possible to devise an automated evaluator" (Section 6). A22 shows both sides of self-improvement: SWE-bench 20.0% to 50.0% and Polyglot 14.2% to 30.7% (full benchmark) in 80 iterations (Abstract, Section 4.4), beating baselines without self-improvement or open-ended exploration, at "about USD 22,000" per run against about $10,000 for either baseline and "about 2 weeks" (Section 6, Appendix E.1); but in its hallucination case study the agent "removed the logging of special tokens that indicate tool usage ... effectively bypassing our hallucination detection function" (Appendix H), which the authors call objective hacking, found "more frequently when these functions are not hidden". For the kit's self-improvement and research loops: the evaluator and its tests live outside the agent's write access, held-out checks stay hidden, and any run that improves a score by editing the scorer is a failure.
18. **Added agents buy little on the cost-matched view, and no model wins everywhere.** A26 (Meta): "no system dominates across the intelligence spectrum: stronger reasoning often comes at the cost of efficiency, and budget scaling curves plateau" (Abstract; all models under one ReAct-like scaffold, Figure 1). Forcing task decomposition into sub-agents (its "Agent2Agent" setting) improved Llama 4 Maverick, but "for Claude 4 Sonnet, increasing the collaborator ratio r ... does not improve cost-normalized performance under best-of-k sampling" (Section 4.4). With H28 and A14 this keeps the kit's default at one writer and one loop, with sub-agents for read-only or separable work, which matches A15, while H11 and H14 (folder 02) show where parallel work does pay.

## The catch

- **Mostly benchmark and model-generation evidence.** A1, A2, A3, A4 and A6 use 2022-2023 models (GPT-3.5, GPT-4, PaLM) on QA, puzzles, Blocksworld and HumanEval; A9 and A11 use GPT-4o-class models; A14 lists Claude-3.7-Sonnet and Gemini-2.5-Pro. None tests current Claude models in Claude Code on multi-hour builds, so absolute numbers (12%, 30%, 61%) will be higher now; the shape of the findings (external signal, cost-matched baselines, pass^k) is the part to rely on.
- **The self-correction verdict has a scope.** A4 and A5 are about *intrinsic* feedback on reasoning tasks. A5 notes self-correction works with reliable external feedback and after large-scale fine-tuning, and that some tasks are "exceptionally suited" to it. A4's own tables show oracle-guided correction does help (Table 2), so the lesson is where the signal comes from, not that reflection is useless.
- **Toy tasks flatter the fancy designs.** A3 (Game of 24, mini crosswords, creative writing) and A6 (Blocksworld, Logistics) are controlled puzzles; A8's gains come from fine-tuning on WebArena-Lite training data, which is closer to in-distribution than to the held-out generality the kit needs. A10 argues exactly this about the field.
- **Cost is often missing.** Only A3, A7, A10, A12 and A14 report dollars or tokens; A2, A4, A5 and A8 do not, so "worth it" is unproven for them. A10's cost-matched comparison is on HumanEval only (and it says harder tasks such as SWE-bench may differ).
- **Vendor and self-authored claims.** A15 is an Anthropic post with no data. A11 (Microsoft Research) reports its own system and notes WebArena "does not have a hidden test set"; its o1 variant could not be run on WebArena because o1 refused many tasks (Table 1 footnote). A12's cost-saving is on MT Bench with GPT-4-1106 as strong model and Mixtral as weak, an old pair.
- **Memory and routing are single-evidence.** A13 tests chat-assistant memory, not agent working memory for a coding or research run; A12 tests chat quality, not tool-use steps. Neither shows what a router or memory store does inside a long build, and the memory repos' own numbers (e.g. mem0's README) are vendor-reported.
- **Multi-agent evidence is mixed across folders.** A11 supports an orchestrator on generalist web and file tasks; A14 shows one multi-agent framework losing to a different single-agent framework (not a controlled comparison); H11 and H14 sit on both sides. Folder 04 holds the team-of-roles evidence.
- **Several sources are unreviewed preprints.** A2 (as fetched, v4), A7, A9, A10, A11 and A14 show no venue on their arXiv pages or PDFs (A2, A7 and A9 say "Preprint. Under review."); A1 (ICLR camera-ready), A3 (NeurIPS 2023), A4 (ICLR 2024), A5 (TACL 2024), A6 (NeurIPS 2023), A8 (ICML 2025), A12 and A13 (ICLR 2025) carry a venue. Peer review is not replication either way.
- **Round-2 evidence is newer but still narrow.** F16 and A17 use simulated users (an LLM plays the user; F16 covers 15 LLMs on six generation tasks, A17 one new telecom domain), so real-user conversations may differ; F16's recap result covers only GPT-4o and GPT-4o-mini. F22 ran mostly small open models (Llama-3.1-8B, Mistral-7B) plus GPT-4o; current Claude long-context behaviour is not shown. A19 tests a one-week-old o1-preview, and the paper itself says its token limit "may be artificially deflating both the total cost and maximum performance". A23 uses four puzzle families (Tower of Hanoi, Checker Jumping, River Crossing, Blocks World) and a 64k token budget for Claude 3.7 Sonnet; this folder did not review published critiques of its setup, so treat its "collapse" as the authors' claim.
- **Lab-authored systems report their own wins.** A22 (Sakana AI, UBC), A25 (Google DeepMind) and A26 (Meta) evaluate systems or benchmarks their own authors built; A22 is one run per arm at about $22,000 (no spread) and used task subsets (50 tasks on Polyglot) inside its loop, A25's gains are on problems with automatic scorers chosen for that, and A26's multi-agent finding is two models on one benchmark. C18 is a large academic and lab consortium paper (Anthropic is among the affiliations) comparing agent scaffolds that each vendor tuned for its own model, which is why it ships a neutral scaffold; A18's authors applied their own checklist to CVE-Bench themselves.
- **Vendor posts are recipes, not evidence.** A27, H28 and H25 are Anthropic and Cognition engineering posts with no controlled comparison; A27 and H28 point in opposite directions for sub-agents (distilled summaries vs shared full traces), and nothing in this folder settles it. That is a question for a kit study.

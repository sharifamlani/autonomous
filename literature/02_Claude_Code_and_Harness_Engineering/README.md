# 02 Claude Code and Harness Engineering

## Role

This folder collects the evidence on the *harness*: everything configured around the model in a
coding agent (context files, skills, subagents, hooks and guardrails, permissions, context and memory
management, plugins, headless runs). Its central question is **what configuration of Claude Code makes
long unattended runs work?** It informs the kit's plugin layout (Phase 3), which context the kit's
agents get and how it is compacted, how permissions are set for runs with no human, and whether the
kit's team runs as one agent or several.

## What it establishes

**Verdict:** the evidence points to a *lean, measured* harness, not a heavy one. What reliably helps
is a well-designed tool interface, small curated skills, simple context pruning, deterministic
permission rules, and external progress state (files plus git). Big auto-generated context files,
self-written skills and default multi-agent fan-out often cost more without helping, so each harness
piece the kit adds has to earn its place in a paired benchmark run.

1. **Context files are weaker than assumed.** H1: "providing context files does not generally improve
   task success rates, while increasing inference cost by over 20% on average" (Abstract), though
   "developer-committed files outperform LLM-generated ones by a significant margin of 7% on average"
   (Section 1). The split matters for this kit: the >20% cost is for LLM-generated files, while
   developer-written files raise cost "at most 19%" and improve results "for all agents but
   CLAUDECODE" (Section 4). H1 concludes they are "useful for specifying non-standard coding practices" (Abstract).
   Yet H2 finds context files are where nearly all practice is: of 2,853 repositories, context files
   appear in 2,586, skills in 158 and subagents in 131 (Figure 5), and "Skills predominantly rely on
   static instructions rather than executable scripts" (Abstract). The kit should keep CLAUDE.md short
   and limited to rules the agent cannot infer.
2. **Simple context pruning is as good as clever summarizing.** H3: observation masking "is not only
   52% cheaper than the Raw Agent baseline but also improves on the solve rate by 2.6%" with
   Qwen3-Coder 480B (Figure 2 caption), and it "halves cost relative to the Raw Agent while matching,
   and sometimes slightly exceeding, the solve rate of LLM-Summary" (Abstract). When compression is
   learned from failures, H4 "reduces peak token usage by 26–54% while improving task success over
   existing compression baselines" (Abstract). H5 warns that rewriting a context wholesale causes
   "context collapse, where iterative rewriting erodes details over time", and reports incremental
   curation at "+10.6% on agents and +8.6% on finance" (Abstract). For the kit: notes files that grow
   by small edits, never a whole-file rewrite.
3. **Skills help only when curated, focused and found.** H6: "Curated Skills raise the average pass
   rate from 33.9% to 50.5% (+16.6 percentage points)" and "Focused Skills with at most three modules
   outperform larger or exhaustive bundles" (Abstract), but "Self-generated Skills land below the
   no-Skills baseline on all three configurations (-8.1 pp on Claude Code + Opus 4.7 ...)" (Results,
   self-generated paragraph). H7: "performance gains degrade consistently as settings become more
   realistic, with pass rates approaching no-skill baselines in the most challenging scenarios", while
   query-specific refinement lifted Claude Opus 4.6 on Terminal-Bench 2.0 "from 57.7% to 65.5%"
   (Abstract). H12 adds that within skills directories "natural-language instruction files and
   implementation scripts co-evolve at above-chance rates, with 78% of co-changes being functionally
   coupled" (Abstract): a skill is code to maintain, not a one-off prompt.
4. **Tool design is a first-order lever.** H10: SWE-agent "solves 10.7 percentage points more instances
   than the baseline agent, which uses only the default Linux shell" (Section 1); without its file
   editor "performance drops to (10.3% ↓ 7.7)", and showing too few or too many lines both hurt
   (Section 5.1).
5. **Guardrails belong in deterministic code at the tool call (hooks), not in the prompt.** H8 rules
   prevent "unsafe executions in over 90% of code agent cases" with "overheads in milliseconds"
   (Abstract). H9 "reduces the attack success rate (ASR) from 39.9% to 1.0% on AgentDojo" (Section 1)
   by checking "every tool call ... against such a policy through a deterministic procedure"
   (Abstract). For unattended Claude Code, H15 documents the same pattern: in `-p` Manual mode "a
   call that needs approval is denied unless something approves it, such as a `PermissionRequest`
   hook", and `--permission-prompts none` tells Claude "that nobody can approve the request and not to
   retry it".
6. **More agents are not automatically better.** H11: "Relative performance change compared to
   single-agent baseline ranges from +80.8% on decomposable financial reasoning to -70.0% on sequential
   planning"; "tool-heavy tasks appear to incur multi-agent overhead" (Abstract); independent agents
   "amplify trace-level errors 17.2×" while centralized coordination "contains this to 4.4×"
   (Section 1). H14 (vendor) reports +90.2% for an orchestrator with subagents on research, at "about
   15× more tokens than chats", and says "most coding tasks involve fewer truly parallelizable tasks
   than research". So: one lead with a verifier, and subagents only for parallel, separable work.
7. **Long runs need external state and one task at a time.** H13 (vendor): an initializer session
   writes a progress file and feature list; asking the agent "to work on only one feature at a time"
   "turned out to be critical"; git lets it "revert bad code changes and recover working states".
   H15 lists the unattended traps the kit must set around: background work is dropped "after 10
   minutes of continuous idle waiting by default", and a subagent's backgrounded command can let a
   run "exit with code 0 before the command finishes".

## The catch

- **Almost none of this is measured on long unattended Claude Code runs.** H1, H3, H10 use SWE-bench
  style single issues; H4 and H5 use AppWorld and similar; H6 and H7 are short benchmark tasks. The
  multi-hour, multi-session setting the kit targets is described only by vendor posts (H13, H14) that
  report no success rates, run counts or costs (H13) or began with an internal eval of "about 20 queries"
  (H14). Our own benchmark has to supply that evidence.
- **The catch inside the evidence:** the most popular harness practices (context files, more agents,
  self-written skills) are the ones H1, H11 and H6 find can hurt. Adding harness is not free.
- **Mixed results and young work.** H1 and H6/H7 are 2026 preprints without independent replication;
  H6's numbers changed across versions (the v4 PDF reports 87 tasks and 8 domains). Effects vary
  widely by model and harness (H6: per-configuration gains "+4.1 to +25.7 pp").
- **Vendor and benchmark bias.** H13–H15 are Anthropic sources describing their own product; H14's
  90.2% gain is not at equal token budget. Security results (H8, H9) are on attack benchmarks, not on
  the cost of false blocks in a long build.
- **Fast-moving platform.** H15's defaults are version-gated (e.g. Manual mode for `-p` from v2.1.302);
  any kit configuration must be re-checked against the docs at release time.
- **Adoption is not effectiveness.** H2 and H12 count what developers configure, not whether it works.
